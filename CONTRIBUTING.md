# Как мы работаем с репозиторием

## Задачи

Каждая работа начинается с задачи в Issues. Стартовый список задач лежит в [docs/backlog.md](docs/backlog.md), а скрипт `tools/github/create_issues.py` заводит их в GitHub разом.

У задачи есть:
- метка команды: `team:auth`, `team:ref`, `team:ops`, `team:data` или `team:all`;
- этап (milestone): «Этап 3», «Этап 4», «Этап 5»;
- номер сценария ПМИ, по которому проверяется результат, и номера ФТ;
- исполнитель (assignee). Берёте задачу, назначьте её на себя, чтобы двое не делали одно и то же.

Задача считается выполненной, когда её сценарий ПМИ проходит на стенде («Описание архитектуры», раздел 6.2).

## Ветки

Ветка `main` защищена: прямые коммиты в неё запрещены, изменения идут только через пулреквест.

Ветка создаётся от свежего `main` и называется `<команда>/<номер задачи>-<коротко>`:

```
auth/12-users-api
ref/20-dependency-cycle
ops/31-operation-patch
data/40-log-filters
all/5-design-buttons
```

```bash
git switch main && git pull
git switch -c ops/31-operation-patch
```

## Коммиты

Пишем по-русски, в повелительном наклонении. В скобках указываем модуль:

```
feat(ops): отметка начала и окончания операции
fix(ref): проверка цикла зависимостей при изменении норматива
test(log): откат изменения без записи в журнал
docs: правила миграций в CONTRIBUTING
```

Типы: `feat` (новое), `fix` (исправление), `test`, `docs`, `refactor`, `chore` (сборка, настройки).

## Пулреквест

1. Один пулреквест решает одну задачу. В описании пишем `Closes #31`, тогда задача закроется сама.
2. Сборка в GitHub Actions должна пройти: компиляция, тесты и проверка границ модулей.
3. Нужно одобрение одного человека из своей команды.
4. Если вы меняете `shared/`, открытый интерфейс модуля (`AuthApi`, `RefApi`, `AuditLog`), миграцию или дизайн-систему (`static/css`, `static/js`), нужно ещё одобрение от каждой команды, которую это затрагивает. Кого звать, подсказывает файл `.github/CODEOWNERS`.
5. Перед слиянием подтяните `main` (`git pull --rebase origin main`) и проверьте, что всё собирается.
6. Сливаем через Squash and merge.

## Границы модулей

- Код своего модуля пишем в своём пакете: `auth`, `ref`, `ops`, `log`.
- Чужой модуль вызываем только через его открытый интерфейс в корне пакета (`RefApi`, `AuthApi`, `AuditLog`). Пакеты `internal` и `web` чужого модуля трогать нельзя: тест `ModularityTests` упадёт.
- Если в чужом интерфейсе не хватает метода, заведите задачу на ту команду. Писать его самим в чужом модуле не надо.
- В базе пишем только в свою схему. Читать в SELECT можно таблицы справочников `ref.*` и `auth.app_user`, остальные чужие данные берём через интерфейс модуля.

## Миграции базы

- Схему меняем только новой миграцией в `src/main/resources/db/migration`. Уже применённые файлы не правим.
- Имя файла: `V<год><месяц><день><час><минута>__<схема>_<что>.sql`, например `V202611051430__auth_drop_password.sql`. Время в имени не даёт двум командам выпустить миграции с одинаковым номером.
- Миграцию проверяет команда «Данные» (она указана в CODEOWNERS).
- После миграции обновите документ «Модель данных» (папка docs/specs) или заведите на это задачу.

## Страницы

- Страницы собираем из компонентов дизайн-системы, см. [docs/design-system.md](docs/design-system.md) и `/styleguide.html`. Свои цвета, шрифты и размеры не заводим.
- Если нужного компонента нет, добавьте его в `static/css/ui.css` и на `/styleguide.html` отдельным пулреквестом с меткой `design`.
- Для запросов к API используем `api` из `/js/api.js`, для ошибок `showError` из `/js/layout.js`. Свой `fetch` не пишем.

## Код

- Java 21, отступ 4 пробела, кодировка UTF-8 (см. `.editorconfig`).
- Ошибки предметной области бросаем как `ApiException` с кодом из спецификации API (`DELAY_CODE_REQUIRED`, `PREDECESSORS_NOT_DONE` и т. д.).
- Метод, который меняет данные, помечаем `@Transactional` и в нём же вызываем `auditLog.record(...)`.
- Право на метод проверяем аннотацией `@PreAuthorize("hasAuthority('код_права')")`. Ограничения на уровне данных («техник видит только свои обороты») проверяем в коде через `CurrentUser.get()`.
- На логику сервиса пишем тест. Названия тестов можно брать из сценариев ПМИ.

## Если что-то сломалось

- Сначала посмотрите requestId в сообщении об ошибке на странице и найдите его в логе сервера.
- Ошибку заводим в Issues по шаблону «Ошибка»: шаги, что ожидали, что получили, requestId.
