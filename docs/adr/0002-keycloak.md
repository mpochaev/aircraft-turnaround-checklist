# ADR-0002. Вход и роли через Keycloak, права ролей в нашей базе

Статус: Keycloak выбран на паре 23.10.2026. Распределение «кто что хранит» предложено, его утверждает команда «Авторизация».

## Контекст

По ЧТЗ нужны:
- вход по логину и паролю, блокировка на 15 минут после 5 неудачных попыток;
- завершение сессии через 45 минут бездействия и через 12 часов после входа;
- несколько ролей у пользователя, настройка прав ролей супервайзером без программиста (ФТ-4–ФТ-15).

Преподаватели разрешили взять Keycloak, команда «Авторизация» его как раз изучает. На паре спросили, как токен проходит через модули монолита и кто проверяет права, когда модуль данных отдаёт информацию.

## Решение

Keycloak отвечает за то, кто вы. Наша база отвечает за то, что вам можно.

| Где | Что хранится | Требования |
|---|---|---|
| Keycloak, realm `checklist` | учётные записи, пароли, политика паролей, блокировка после 5 попыток на 15 минут, сессии 45 минут и 12 часов, роли и их назначение пользователям | ФТ-4–ФТ-7, ФТ-9, ФТ-10 |
| `auth.permission` | справочник прав (21 код из таблицы 3.1 спецификации) | ФТ-11, ФТ-12 |
| `auth.role` + `auth.role_permission` | какие права у роли. Код роли совпадает с именем роли в Keycloak | ФТ-11 |
| `auth.app_user` | логин и ФИО для экранов, журнала и назначения техника | ФТ-25, ФТ-40 |
| `auth.change_request` | заявки на изменение ФИО и сброс пароля | ФТ-13–ФТ-15 |

Как это работает в коде:
1. Страница получает токен у Keycloak (клиент `checklist-web`, вход по коду с PKCE).
2. Сервер проверяет токен на входе. Роли берёт из `realm_access.roles`, права к ним из `auth.role_permission`.
3. Модули токена не видят, им доступен только `CurrentUser`. Подробно в [architecture.md](../architecture.md).

Действия супервайзера из ЧТЗ сервер выполняет через Admin API Keycloak:
- создать сотрудника, назначить роли, сбросить пароль, разблокировать, отключить;
- создать роль.

Права роли меняются только в нашей базе.

## Что поменять в документах (задача команды «Авторизация»)

- **Спецификация API, раздел 5.** Методы `POST /auth/login`, `POST /auth/logout` и `PATCH /me/password` уходят в Keycloak. Страница входа и смена пароля будут страницами Keycloak.
  - `POST /auth/password-reset` остаётся у нас, потому что по ФТ-14 сброс идёт через заявку супервайзеру.
  - Методы `/users` и `/roles` остаются, но внутри обращаются к Admin API Keycloak.
- **Модель данных.** Новая миграция убирает из `auth.app_user` поля `password_hash`, `failed_attempts`, `locked_until` и таблицу `auth.user_session`. Таблица `auth.user_role` больше не нужна, роли пользователя хранит Keycloak. В `auth.app_user` можно добавить `keycloak_id uuid` для связи.
- **ПМИ.** В сценариях 1–8 проверяется вход через страницу Keycloak. Коды 401 и 423 из спецификации заменяются сообщениями Keycloak.

## Последствия

- Код входа, хранения паролей и блокировки писать не нужно, оценка компонента «Авторизация» уменьшается.
- Появляется зависимость от Admin API Keycloak. Для разработки без Keycloak есть профиль `dev`.
- Страница входа Keycloak по умолчанию тёмная. Тему в стиле дизайн-системы делает команда «Авторизация» (задача в backlog).
